# Устройство Ритма

## Хранение и расчеты

Оба клиента используют запись `Entry`: ID, календарная дата, направление платежа, сумма в копейках, категория, контрагент и комментарий. Контракт описан в `shared/entry.schema.json`. Начальные данные собраны в одном файле и копируются в ресурсы клиентов скриптом `scripts/seed.py`.

UI не хранит отдельные итоги. Показатели, категории и графики вычисляются из списка операций. Это исключает рассогласование между журналом и карточками после редактирования.

### Android

```text
Compose screens
      |
LedgerViewModel / StateFlow
      |
LedgerRepository
      |
Room / SQLite
```

Работа с базой и файлами выполняется вне главного потока. Room публикует обновления через Flow. ViewModel сохраняет состояние данных при изменении конфигурации. Экран и выбранный месяц используют rememberSaveable.

CSV читается и сохраняется через Android Storage Access Framework. Приложение не требует общего доступа к файловой системе. Автоматическое системное резервирование базы выключено; перенос записей выполняет пользователь через экспорт.

### Web

Функции в `domain/ledger.ts` не зависят от React. Хук `useLedger` читает и проверяет localStorage, сохраняет валидированный список и только затем обновляет состояние интерфейса. Ошибка записи не превращается в ложное сообщение о сохранении.

CSV обрабатывается Papa Parse. Диалог операции использует нативный HTML dialog: фокус остается внутри модального окна, Escape закрывает форму. Все кнопки с иконками имеют доступные названия.

### Python

`ledger.py` читает и проверяет данные, `report.py` отвечает за представление. pandas используется для группировок, matplotlib для графиков и файлов PNG/PDF. Все денежные итоги до финального отображения рассчитываются в целых копейках.

## Перенос данных

Web и Android автономны. Экспорт включает стабильные ID, поэтому повторная загрузка файла не удваивает операции. Импорт добавляет только отсутствующие ID, а не перезаписывает существующие записи. Это сознательная граница простого обмена, не двусторонняя синхронизация с разрешением конфликтов.

## Дальнейшее развитие

Для совместного учета потребуется серверный источник данных, авторизация, изоляция рабочих областей, история изменений и протокол разрешения конфликтов. Для подключения банка потребуются отдельные адаптеры, согласия и проверки доступных API. Эти функции не имитируются локальными кнопками.
